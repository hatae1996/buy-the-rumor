# 0.2.0 작업 목록 (서버) — 계획 초안

기준: `docs/기획서.md`(0.1.3) "멀티플레이 구조", "시간과 접속 리듬", "알림", CHANGELOG 0.1.3, `docs/handoff/0.1.3.md` 1번(세계 여러 개 + 합친 랭킹은 0.2.0).
아직 0.2.0 기획(handoff)이 오지 않아, 0.1.3까지 만든 것과 기획서로 짠 **개발 쪽 계획**이다. 기획에서 정할 것은 `docs/questions.md` 104번부터.

## 목표

아이폰 사파리로 여는 비공개 테스트를 서버 위에서 한 시즌 돌린다: 로그인 → 세계 배정 → 명령 보내기 → 서버가 하루를 돌림 → 다시 열면 "자리를 비운 사이" → 시즌 결산과 시즌 전체 랭킹.
시뮬레이션 코드(`src/sim`)는 고치지 않고 그대로 서버에서 부른다(구조 원칙 1~5를 지켜 온 이유).

## 지금 가진 것 (0.1.3)

## 순서와 이유

서버에서 하루가 도는 것(1~3)을 먼저 만들고, 그 위에 사람(4~6), 여러 세계와 랭킹(7~8), 화면(9~10)을 얹는다. 비공개 테스트 전에 봇으로 한 시즌을 서버에서 끝까지 돌려 본다(11).

## 1. Supabase 프로젝트, 표 설계

- 표 (초안):
  - `seasons`: 시즌 id(여는 날 `2026-10-26` 꼴), 시드(`seasonSeed`), 마을 수, 여는 때, 끝나는 때, 상태(열림 / 결산 / 끝).
  - `worlds`: 세계 id, 시즌 id, 인원, 상태 JSON(`EconomyState`), 맵은 시드와 마을 수로 다시 만든다(저장하지 않음), 마지막으로 돌린 날, 버전(낙관적 잠금).
  - `members`: 계정 ↔ 세계 ↔ 플레이어 id(계정 id를 그대로 플레이어 id로: 시즌 전체 순위에서 id가 겹치지 않아야 한다, `ranking/table.ts`).
  - `certificates`: 계정마다 상인 증서(인장, 칭호, 연차). 시즌을 넘어 남는 것.
  - `score_rows`: 날마다 세계별 점수 줄(`ScoreRow`). 시즌 전체 순위는 이 표를 모아 매긴다.
  - `day_reports`: 플레이어마다 그날 요약(알림 거리, 장부 줄). "자리를 비운 사이"에 쓴다.
  - `commands`: 받은 명령 기록(시험과 부정 검사용, 상태를 다시 만들 수 있게).
- 상태는 세계마다 JSON 하나로 둔다(1MB 안팎). 표로 쪼개지 않는다: 시뮬이 상태 전체를 한 번에 다루고, 정산은 세계 하나 안에서만 일어난다.
- 행 수준 보안(RLS): 폰은 `worlds`를 직접 읽지 못한다. 화면 데이터는 서버 함수만 만든다(숨은 숫자가 폰에 오지 않게, 기획서 "플레이어가 알 수 있는 정보만 보낸다").

## 2. 시뮬을 서버에서 부르기

- `src/sim`을 Deno에서 불러올 수 있게 번들 하나로 묶는다(`npm run build:sim`, esbuild 또는 Vite 라이브러리 빌드). Edge Function은 이 번들만 부른다.
- 서버 함수: `command`(명령 하나 적용 → 화면 데이터), `view`(화면 데이터), `tick`(세계 하루), `season`(열기·결산).
- 같은 시드·같은 명령이면 같은 결과인지 서버와 로컬을 맞춰 보는 시험: 로컬에서 돌린 세계와 서버에서 돌린 세계의 상태 해시가 같다.

## 3. 하루 돌리기

- 하루 = 실제 2시간 30분(지금 로컬과 같다, `DAY_MS`). pg_cron이 장날 시각에 `tick`을 부르고, 세계마다 `advanceDay` 한 번. 밤에도 돈다(확정, 0.0.9).
- 명령과 장날이 겹치지 않게 세계마다 잠근다(행 잠금 또는 버전 비교). 장날이 도는 동안 온 명령은 다음 날 신청으로 받는다.
- 늦어지거나 빠진 장날은 다음 `tick`이 밀린 날만큼 돌린다(로컬의 `catchUp`과 같은 방식).
- 하루를 돌린 뒤 점수 줄(`scoreRows`)과 플레이어별 요약을 표에 남긴다.

## 4. 로그인과 계정

- Supabase Auth. 기획서는 애플·구글 로그인. 사파리 웹 테스트에서 무엇으로 할지는 질문 109.
- 처음 들어오면 상단 이름과 문장을 고른다(지금 견습 끝의 "상단 이름 짓기"). 이름 금칙어 걸러 내기(보류 항목)를 여기서.

## 5. 명령 받기와 화면 데이터

- 폰은 명령(`Command`)만 보내고, 서버가 `applyCommand` → 상태 저장 → `playerView`를 돌려준다. 실패는 지금처럼 오류 이름으로.
- 원정 카드처럼 난수가 드는 명령도 서버에서만 정한다(지금도 시뮬 안 시드 난수라 그대로).
- 견습: 지금은 세계 안의 한 마을에서 세계 전체를 멈추고 한다. 공유 세계는 멈출 수 없어, 기본안은 세계 밖의 혼자 쓰는 작은 세계에서 하고 졸업하면 그날의 공유 세계에 들어가는 것(질문 111).

## 6. 자리를 비운 사이

- 로컬은 지나간 날을 그 자리에서 돌리며 요약을 만든다(`Game.catchUp`). 서버는 날마다 플레이어별 요약(`dayNotices`, 장부 줄, 들은 소문, 도장)을 남겨 두고, 다시 열면 마지막으로 본 날부터 모아 보낸다.
- 알림(푸시)은 질문 110.

## 7. 시즌 열기, 세계 배정, 시즌 중간 참가

- 시즌 여는 날 시즌 하나(시드 = `seasonSeed(시즌 id)`)를 만들고, 들어오는 사람을 세계에 배정한다. 같은 시즌의 세계는 모두 같은 시드, 같은 마을 수(질문 104, 105).
- 배정(초안): 인원이 가장 적고 15명이 안 된 세계에. 다 찼으면 새 세계를 연다. 새 세계는 같은 시드로 미리 돌리기(20일)부터 오늘까지 돌려 같은 날에 맞춘다(하루 11ms라 13일 치 120일이 2초 안).
- 시즌 중간 참가는 10일째까지(기획서 초안).
- 인원을 봇으로 채울지는 질문 108.

## 8. 시즌 전체 랭킹과 결산

- 장날마다: 세계를 다 돌린 뒤 `score_rows`를 모아, 세계마다 `updateRankings(state, 다른 세계 줄)`. 화면에는 시즌 전체 순위와 내 세계 순위(0.1.3에서 만든 화면). 봇을 시즌 전체 순위에서 뺄지는 질문 108.
- 마지막 장날 뒤: 모든 세계를 다 돌린 다음 `settleSeason(state, 다른 세계 줄)`. 인장과 칭호는 시즌 전체 순위로, 증서는 `certificates` 표에 옮긴다.
- 명예의 전당(시즌마다 부문 1위 기록) 표를 둔다.

## 9. 화면

- 지금 `src/ui/game.ts`의 `Game`(로컬 저장, 지나간 날 돌리기, 봇)을 같은 모양의 두 갈래로 나눈다: 로컬 게임(지금 그대로, 개발과 혼자 하기)과 서버 게임(명령을 보내고 화면 데이터를 받는다). 화면 코드는 `view()`와 `dispatch()`만 보므로 거의 그대로 둔다.
- 서버 게임은 `dispatch`가 비동기가 된다. 보낸 뒤 답이 올 때까지 단추를 잠그고, 통신이 끊기면 "다시 연결 중" 표시.
- 지도의 다른 상단(말), 신문, 랭킹은 서버 화면 데이터에서 그대로.

## 10. 개발용 관찰 화면

- 지금 `dev.html`(모든 숫자, 봇 돌리기)에 "서버 세계 열기"를 더한다: 세계 상태 JSON을 받아 그대로 보여 준다(운영자만).

## 11. 봇으로 서버 시즌 한 번

- 서버에 봇 12명 세계 둘을 열어 시즌을 끝까지 돌린다(시간을 빠르게 하는 시험 모드). 확인할 것: 장날이 빠지지 않는다, 같은 시드 세계 둘의 사건 일정이 같다, 시즌 전체 랭킹과 결산, 상태 크기와 함수 시간.
- 그다음 비공개 테스트(질문 107).

## 하지 않는 것
